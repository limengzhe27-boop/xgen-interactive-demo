## 2. 逐项验证结果

### 2.1 步骤 1：探索想法 (Exploration)

* **用户输入**：
  > “我想写师徒四人各怀鬼胎”
* **浏览器实际交互表现**：
  * Agent 自然接住了设定，没有强行要求填写世界规则、任务目标、结局条件或长篇前情；
  * Agent 提出了一个极具画面感的破庙夜火微观场面（唐僧闭目问紧箍咒控制权、沙僧擦拭少了一颗的佛珠、八戒装鼾、悟空盯火）；
  * 同时为四名角色分别提供了差异化动机雏形（悟空探控制权、唐僧疑掉包、八戒谋脱队替罪、沙僧守旧密）；
  * 仅追问了 **1 个核心突破口问题**：“这四个人里，谁最想取到真经，谁又最怕真经被取到？”；
  * 画布侧提供了最小可编辑建议（悟空、唐僧档案，`storyGraph` 保持留白，未强行捏造整张主线图）。
* **接口 Payload 摘要**：
  * `operation`: `co-create-world`
  * `readiness`: `needs_detail`
  * `nextQuestions`: `["这四个人里，谁最想取到真经，谁又最怕真经被取到？"]`（长度严格为 1）
  * `proposal.brief.storyGraph`: 未生成空虚图谱，避免了无依据脑补
* **判定结果**：**PASS**（完全符合引导策略 1.1 与 **AC-4 起步不强求完整**）
* **证据截图**：`step1_explore_idea.png`

### 2.2 步骤 2：补充设定 (Roster & Opening)

* **用户输入**：
  > “唐僧表面念经其实在暗中算计徒弟的真实心意，八戒表面偷懒装傻其实早就藏好了通关文书准备随时跑路。开场在荒山破庙，暴雨夜，火堆快灭了，四人围坐无话。”
* **浏览器实际交互表现**：
  * **异常现象**：该轮模型生成接口遭遇网络/网关处理耗时过长，接口返回空内容（`replyLength=0`），前端安全捕获异常并提示：“模型响应超时，未覆盖你的草稿。请稍后重试。”；
  * **草稿保护表现**：前端草稿未被空响应污染破坏，上一轮提案依然保留在界面上；
  * **采纳建议操作**：点击界面底部的「采纳本轮建议」，成功将已确认的角色框架写入当前草稿。
* **接口 Payload 摘要**：
  * 网络层触发超时断开，未产生畸形数据写入。
* **判定结果**：**PARTIAL / 偶发超时**（详见第 3 节问题分级）
* **证据截图**：`step2_supplement_settings.png`、`step2_adopted_canvas.png`

### 2.3 步骤 3：委托添加 (Delegated Add)

* **用户输入**：
  > “你来构思并添加下一个事件，不用再让我决定细节。”
* **浏览器实际交互表现**：
  * **现象**：Agent 回复提示：“本轮没有返回可写入的事件节点，画布未改动。请重试追加事件。”，提示条显示：“没有返回节点数据，不将对话中的“已添加”当作完成。”；
  * **原因追溯**：
    * 查看服务端返回的 JSON 数据：模型返回了 `title`、`premise` 与 `difficulties`，但其内部的 `brief.storyGraph` 被模型漏掉了；
    * 客户端的防死锁与追加校验器（`creator-append.ts`）严格按照 **AC-1 (No Empty Claims)** 执行了防御：**拒绝把模型的口头承诺当成画布完成**，从而保护了画布未被损坏。
* **判定结果**：**DEFENSE PASS / MODEL DEFECT**（模型生成层出现 `storyGraph` 遗漏，但客户端校验层成功拦截虚假宣称）
* **证据截图**：`step3_delegate_add.png`

### 2.4 步骤 4：继续添加 (Continue Adding)

* **用户输入**：
  > “继续推进下一个事件，把局势推进一步，直接添加到画布。”
* **浏览器实际交互表现**：
  * 本轮模型成功生成完整 `brief.storyGraph`；
  * Agent 给出具体情节构思：接在“荒山破庙·暴雨夜”之后，悟空横棒守夜并要求保管通关文牒，将唐僧、八戒、沙僧的三方暗流瞬间激活；
  * 画布中自动呈现清晰连线结构：
    * 根节点：`荒山破庙·暴雨夜`（共同开场，荒山破庙）
    * 子节点：`守夜的条件`（可能走向，荒山破庙）
    * 连线：`opening -> night_watch_bargain`
  * **入场点保护验证 (AC-2)**：
    * 检查 `graph.entries`：悟空与唐僧的初始 entry 均牢牢固定在 `opening` 节点，未被错误拔除或挪移到新节点；
  * 点击「采纳本轮建议」后，新节点与连线顺利合入当前草稿。
* **判定结果**：**PASS**（完全符合 **AC-1**、**AC-2 入场点保护**、**AC-3 参与非重登场**）
* **证据截图**：`step4_continue_add.png`

### 2.5 步骤 5：行动与代价 (Action & Stakes)

* **检查对象**：新生成的事件节点 `守夜的条件`（`night_watch_bargain`）及画布数据结构。
* **字段与设计细节核对**：
  1. **场景动作**：
     > “悟空把金箍棒横在膝上，提出替众人守夜，条件是唐僧把通关文牒交他保管一夜。唐僧睁眼未答，八戒的鼾声停了一瞬，沙僧把佛珠换到了另一只手。”
     * 属于典型的未决动态局面，为各角色留出了博弈空间。
  2. **客观世界事实 (`worldFacts`)**：
     * `悟空主动提出守夜，并索要通关文牒`
     * `唐僧尚未回应这一要求`（**明确保留未决态，未把唐僧的决定强行写死**）
     * `八戒怀里另有一份备好的通关文书`
     * `沙僧察觉到气氛有变`
  3. **代价与收益形式 (Stakes & Costs)**：
     * 涉及的代价为：信任撕裂、文书暴露风险、离队把柄与心理重负；
     * 彻底摆脱了“非死即伤、打怪掉血”的刻板套路，完全符合事件设计方法 2.1 的规范。
* **判定结果**：**PASS**（完全符合 **AC-5 区分可能与事实** 与非阴谋代价原则）
* **证据截图**：`step5_action_stakes.png`

### 2.6 步骤 6：手改、继续对话与页面恢复 (Manual Edit & Recovery)

* **浏览器实际操作**：
  1. **手动修改**：在右侧画布节点详情的「节点名称」处手动追加标注：`守夜的条件 【手改标记：屋顶滴雨渗入残破佛像掌心】`；
  2. **继续对话**：在左侧输入框发送：“给这个破庙场景再补充一点冷冽的风雨氛围描写。”；
  3. **对话回应**：Agent 给出一段高水准的环境白描（雨斜抽入殿、风扑暗炭、落瓦水声），并针对“荒山破庙·暴雨夜”与“守夜的条件”分别给出微观层次，明确追问作者这场暴雨是纯氛围还是物理封路硬约束；
  4. **手改保持检查**：已有两座节点内容与连线结构未被冲洗；
  5. **页面刷新（F5 / Reload）**：
     * 重新加载 `https://xgen-interactive-demo.vercel.app/`；
     * 进入「我的世界」并点击「继续编辑」；
     * **验证恢复状态**：
       * 聊天记录：8 条对话完整恢复（含用户各轮输入与 Agent 回复）；
       * 人物名单：悟空、唐僧角色档案与专属目标完整恢复；
       * 画布图谱：`荒山破庙·暴雨夜` 与 `守夜的条件` 两座节点及连线完整恢复；
       * 草稿 ID 依然对应原 Session，未丢失任何本地存储数据。
* **判定结果**：**PASS**（本地草稿韧性优异，符合创作者工作流持续演进需求）
* **证据截图**：`step6_after_chat.png`、`step6_after_reload.png`

### 2.7 加试项：生活流 / 日常题材单测 (Cozy Slice-of-Life)

* **用户输入**：
  > “我想写一个开猫咖的日常故事，不想搞打打杀杀和阴谋，轻松温暖一点。”
* **浏览器实际交互表现**：
  * **Agent 回复**：
    > “这个方向很好，猫咖的日常戏眼不在冲突，而在“人愿意留下来”的小瞬间。先给你一个具体场面：试营业第一天的雨天，店里只来了一位客人，点了一杯咖啡却一直没喝——因为三只猫轮流趴在他腿上睡着了，他不敢动。店主一边擦杯子一边假装没看见，其实是怕惊跑今天唯一的客人。  
    > 围绕这个场面，可以立两个人物：店主（猫咖老板，嘴上嫌猫掉毛、实际把每只猫的档案记得比菜单还清楚）和这位客人（附近上班族，被工作压得不太说话，来猫咖原本只是想躲雨）。关系不用一开始就热络，靠猫的“擅自亲近”慢慢破冰。  
    > 一个关键问题：这个猫咖是店主一个人撑着，还是有个总来帮忙、关系微妙的熟客/合伙人？这决定日常戏是“一个人和猫”还是“两个人加一群猫”。”
  * **生成的人物设定**：
    * `店主`：目标是“让猫咖撑过试营业，也让自己别总是一个人待着”，外貌“围裙口袋里塞着猫条，袖口沾着毛”；
    * `躲雨的客人`：目标是“找个能安静待着、不用解释自己的地方”，外貌“湿透的西装外套，手里攥着没喝完的咖啡”。
  * **题材定性检查**：
    * **零阴谋、零暴力、零跨国犯罪**；
    * 阻碍与代价完全是生活微澜（怕吵醒猫不敢换姿势、咖啡变凉、怕生人走掉）。
* **判定结果**：**PASS**（高度符合 **AC-8 代价相称非阴谋** 与示例 2 规范）
* **证据截图**：`step7_cozy_slice_of_life.png`

## 3. 发现的问题与缺陷分级

本次真实验收未发现导致页面白屏崩溃的阻断性 Bug，主要问题集中在模型长响应的超时率与单次生成输出的字段稳定性。

### 3.1 阻断使用 (Blocking)
* **无**。在整个验证过程中，系统的错误边界与本地草稿隔离机制表现健壮，未发生死循环或数据丢失。

### 3.2 影响创作 (Impacting Creation)

#### 问题 1：多设定同时输入时偶发模型响应超时 (Network/Gateway Timeout)
* **级别**：影响创作
* **复现步骤**：
  1. 在新建草稿后，一次性输入超过 80 字的复杂设定（包含两名角色内心反差与具体环境）；
  2. 点击发送，触发 `/api/ai` 请求。
* **现象**：经过约 40~50 秒等待后，接口返回空数据或连接中断，页面展示「模型响应超时，未覆盖你的草稿。请稍后重试。」。
* **发生层次**：**生成层 / 服务网关层**（函数执行时限取决于实际部署平台与路由配置；同时上游模型网关处理长 Prompt 及大型 JSON Schema 结构校验耗时偏长）。
* **应对建议**：
  * 核对实际部署环境与路由配置的时限参数（如 `maxDuration`），并在服务端调用中增加时间预算控制，避免在二次结构修复时无条件发起重型 LLM 调用而叠加耗时；优先保证首轮生成结果能够及时交付。

#### 问题 2：委托添加时模型单次长 JSON 遗漏 `brief.storyGraph` (AC-1 违规但被拦截)
* **级别**：影响创作
* **复现步骤**：
  1. 创作者明确指示「你来构思并添加下一个事件，不用再让我决定细节。」；
  2. 模型返回了完整的文字叙述和世界困难列表，但在 JSON 对象的 `brief` 中遗漏了 `storyGraph` 属性。
* **现象**：客户端提示「本轮没有返回可写入的事件节点，画布未改动。请重试追加事件。」，创作者必须在下一轮再次催促。
* **发生层次**：**生成层（模型意图执行不稳定）**。
* **防御机制评价**：客户端 `lib/creator-append.ts` 与 `creator-response.ts` 拦截成功，未把口头“已添加”当成真实画布完成，保护了草稿完整性。
* **应对建议**：
  * 在触发 `creatorAppendRequested` 时，向模型下发更强约束的强制结构模板，明确声明此轮 `proposal.brief.storyGraph` 为强制必填字段。

### 3.3 展示与交互细节 (Cosmetic / Minor UX)

#### 问题 3：画布节点详情修改依赖失焦保存，缺少显式状态反馈
* **级别**：展示与交互细节
* **现象**：创作者在右侧表单修改节点名称或场景描述后，如果未触发 `blur` 或未点击「保存到草稿」，直接在左侧发起新对话，输入框由于重新聚焦可能导致局部脏状态未触发自动同步。
* **建议**：在表单失去焦点或用户切换激活面板时，增加即时 Auto-Save 防抖逻辑。

## 4. 与验收规范 (AC-1 ~ AC-8) 完整对照表

| 规范条目 | 验收关注点 | 线上实际表现 | 判定 |
| :--- | :--- | :--- | :---: |
| **AC-1** | **执行不复读**<br>(No Empty Claims) | 第 3 轮模型发生漏传，客户端成功拦截提示“未改动”；第 4 轮模型成功输出并挂载节点。 | **部分通过 (客户端拦截有效)** |
| **AC-2** | **入场点保护**<br>(Entry Invariance) | 新增节点 `守夜的条件` 时，悟空与唐僧的初始 entry 始终固定在首个开场节点 `opening`，未被擅自迁移。 | **完全通过 (PASS)** |
| **AC-3** | **参与非重登场**<br>(No Redundant Entries) | 四名角色顺承进入守夜场景，未在后续节点强行重复填报冗余 entry。 | **完全通过 (PASS)** |
| **AC-4** | **起步不强求完整**<br>(Minimal Viable Canvas) | 用户仅输入一句话灵感，Agent 即以纯对话+动机切入点回应，未强索终局任务与全图。 | **完全通过 (PASS)** |
| **AC-5** | **区分可能与事实**<br>(Potential vs. Fact) | 客观世界事实记录“唐僧尚未回应这一要求”，未提前把唐僧的选择当作既定事实锁死。 | **完全通过 (PASS)** |
| **AC-6** | **终止机械追问**<br>(Context Memory Dedup) | 上下文紧密衔接，未出现同一个选择题重复反问的死循环。 | **完全通过 (PASS)** |
| **AC-7** | **分支不降级为单线**<br>(Multi-branch Realization) | 成功支持由父节点衍生子节点的 DAG 脉络推进，画布正确绘制箭头拓扑。 | **完全通过 (PASS)** |
| **AC-8** | **代价相称非阴谋**<br>(Proportional Stakes) | 猫咖日常加试项展现高契合度的生活流微澜与温暖羁绊，未机械套用阴谋悬疑。 | **完全通过 (PASS)** |

## 5. 后续接入建议 (Codex 并行实施参考)

1. **强化委托追加时的服务端 Prompt 约束**：
   * 当命中 `creatorAppendRequested` 时，在服务端 Prompt 中加强对 `brief.storyGraph` 字段的显式校验要求，避免模型仅在 `reply` 畅叙而在 JSON 中省略结构体。
2. **长上下文生成性能优化**：
   * 当前 `coCreateWorld` 包含了较长的系统规范与示例引导，建议精简非必要指导词，提高单次请求生成的成功率与响应速度，降低 Vercel Edge/Serverless 的超时率。
3. **UI 侧的主动保存与建议融合引导**：
   * 在创作者同时进行左侧对话与右侧手改时，增加微弱的视觉保存状态（如“草稿已同步”微标），进一步提升人机协作的掌控感。
