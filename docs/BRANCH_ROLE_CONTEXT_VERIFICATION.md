## 一、复核结论总览

| 检查项 | 判定结果 | 核心发现摘要 |
| :--- | :---: | :--- |
| **1. 切换角色不跳事件** | **通过** | 在后续事件节点切换角色视角，选中节点严格保持；仅在显式点击人物档案“查看与修改入场”时才跳至角色登场节点。 |
| **2. 早入场不等于当前在场** | **失败** | 仅凭拓扑先后顺序直接判定「该角色已在局中」，把“更早入场”强行推断为“在此事件在场/知情”，缺乏角色实际登场或参与依据。 |

| **4. 行动归属匹配** | **失败** | 使用纯字符串 `includes` 双向匹配导致：①“陆沉”与“陆沉舟”行动互相串流；②被突袭目标写在参与者中被误当成行动者；③角色改名导致历史行动全部失效。 |
| **5. 就地补充与保存** | **通过** (存体验缺陷) | 就地补充行动立即保存，不改变任何角色首次入场；草稿与 Agent 建议严格隔离；达到 6 项上限时原生按钮禁用，但缺少“已达上限”明确提示文案。 |

## 二、逐项复核详情与证据

### 1. 切换角色不跳事件

- **判定**：**通过**
- **最短复现步骤**：
  1. 在故事画布中建立 4 个节点（`共同开场` → `节点2` → `节点3` → `节点4`）。
  2. 角色 1（许知遥）入场在开场，角色 2（陆沉）入场在节点 2。
  3. 在角色 1 视角下点击选中 `节点3`（高亮显示节点3）。
  4. 顶部切换角色为角色 2。
  5. 检查画布选中节点：依然保持在 `节点3`，未跳回 `节点2`（`pressedIndex: 2`）。
  6. 切换至「人物设定」Tab，在角色 2 档案中点击「查看与修改入场」。
  7. 检查画布：自动切回「故事脉络」Tab，并精确跳转选中角色 2 的入场点 `节点2`（`pressedIndex: 1`）。
- **数据与截图证据**：
  - CDP 测试输出：
    - `Check 1 Node under Role 1: 2, under Role 2: 2`
    - `Check 1 After clicking jump: { pressedIndex: 1, title: '节点2' }`
  - 截图证据：`trc_check1_switch_preserves_node.png`
- **结论与性质**：
  - **实际复现确认通过**。切换角色仅变更视角，不会意外重置创作者正在构思的节点。

### 2. 早入场不等于当前在场

- **判定**：**失败（存在认知与逻辑过度推断）**
- **最短复现步骤**：
  1. 角色 2（陆沉）首次入场设定在 `节点2`（如客栈前厅）。
  2. 创作者选中后续节点 `节点4`（如地底密室暗格，剧情设定为角色 1 独自潜入探查，陆沉仍在客房未在场）。
  3. 切换视角至角色 2（陆沉），查看右侧面板「陆沉 · 与此事件的关系」。
- **实际呈现内容**：
  - 界面赫然展示：
    > **「陆沉」已在更早的节点「节点2」入场，发生此事件时该角色已在局中。**
- **问题分析**：
  - **实际复现的问题**：在 `components/creator-story-canvas.tsx` 第 270 行：
    ```tsx
    isAfterEntry ? `「${roleName}」已在更早的节点「${entryNode?.title || '入场点'}」入场，发生此事件时该角色已在局中。`
    ```
  - **认知推断错误**：
    1. **拓扑先后 ≠ 物理在场**：角色在故事图较早节点登场，绝不代表在后续任一事件中都在场（可能在另一地点待命、睡着或独自行动）。
    2. **拓扑先后 ≠ 知情/参与**：“已在局中”在叙事理解上强烈暗示该角色知晓或卷入该事件，直接违背了“仅凭图上先后顺序不能证明在场、知情或参与”的原则。
    3. 在该事件未显式配置角色参与时，系统应当中立表述为“已在更早节点登场；未设定该角色是否在场或知晓此事件”，而非断言“已在局中”。
- **截图证据**：
  - 截图证据：`trc_check2_early_entry_claimed_in_game.png`（清晰展示文案断言：“发生此事件时该角色已在局中”）。

### 3. 互斥分支不串联

- **判定**：**失败（汇合节点发生前史串联与过度推断）**
- **拓扑结构构造**：
  - `共同开场`（分岔路口）
    - 走向 A：`走山路`（角色 2 在此首次入场） → `渡口汇合`（汇合节点）
    - 走向 B：`走水路`（互斥分支，角色 2 未登场） → `渡口汇合`（汇合节点）
- **分情况复核**：
  - **情况 3.1（查看互斥分支 B）**：
    - 角色 2 视角下点击 `走水路`。
    - 界面提示：`「陆沉」首次体验从「走山路」（位于另一走向）开始，查看此事件不会改变其入场。`
    - **此分支表现正常**：未把 A 强行拼入 B，明确标注位于另一走向。
  - **情况 3.2（查看汇合节点 `渡口汇合`）**：
    - 角色 2 视角下点击 `渡口汇合`。
    - 故事图从开场到汇合节点存在两条路径：
      - 路径 1：`['开场', '走山路', '渡口汇合']`（经过入场点）
      - 路径 2：`['开场', '走水路', '渡口汇合']`（不经过入场点）
    - 代码逻辑（第 262 行）：
      ```tsx
      const isAfterEntry = paths.some(p => p.includes(entry?.nodeId ?? ''));
      ```
    - 因为路径 1 包含 `走山路`，`paths.some()` 判定为 `true`。
    - **实际呈现文案**：
      > **「陆沉」已在更早的节点「走山路」入场，发生此事件时该角色已在局中。**
- **问题分析**：
  - **实际复现的问题**：混淆了**“图上某条走向可达”**与**“实际游玩经历”**。
  - 若玩家在实际互动中选择走向 B（走水路），整个过程根本没有发生走向 A，角色 2 也未曾入场。此时汇合点对该玩家而言是一个“角色 2 尚未登场”的局面。
  - 界面却基于全图的 `paths.some` 宣布角色“已在局中”，直接把走向 A 的经历预设为汇合点的普适前史，造成互斥分支在汇合点串联。
  - **规范建议**：当一个节点存在多条上游走向且部分走向不包含该角色入场点时，不能断言“已在局中”，必须说明：“取决于此前走向：若经由「走山路」该角色已登场；若经由其他走向则尚未入场”。

### 4. 行动归属匹配

- **判定**：**失败（字符串匹配存在多处误判与脆弱性）**
- **代码实现审查**（`components/creator-story-canvas.tsx` 第 264 行）：
  ```tsx
  const rolePossibilities = (node.possibilities ?? []).filter(
    p => p.actor && (p.actor.includes(roleName) || roleName.includes(p.actor))
  );
  ```
- **实际复现与代码推断问题**：
  1. **名字子串冲突（包含匹配导致劫持）**：
     - 当前角色为 `陆沉`，节点上存在另一角色 `陆沉舟` 的可能行动 `{ actor: "陆沉舟", action: "施展剑法" }`。
     - 由于 `"陆沉舟".includes("陆沉") === true`，该行动被错误展示在 `陆沉` 的行动面板中。
     - 反之，若当前角色为 `陆沉舟`，`roleName.includes(p.actor)` 也会将 `陆沉` 的行动全部拉取过来。两者行动严重互相污染。
  2. **被提及/被攻击对象被误当成行动者**：
     - 当节点记录敌对事件 `{ actor: "黑衣刺客（突袭陆沉）", action: "射出淬毒袖箭" }`。
     - 由于 `actor` 文本中包含“陆沉”，系统错误判定这是陆沉的行动，归并在“「陆沉」在此事件中的可能行动与反应”下方。被攻击的受害者被误列为刺客行动的主体。
  3. **角色改名导致全部行动脱钩（孤立数据）**：
     - `node.possibilities` 中的 `actor` 存放的是纯文本姓名（如 `"陆沉"`），而不是稳定的角色标识（如 `roleId` 或 `editorId`）。
     - 当创作者在人物设定中将角色姓名改为“陆先生”或“陆掌柜”时，`roleName` 变为新名字，之前配置的所有行动立刻全部失配，界面显示为“暂未配置专属可能行动”，原有配置看似“丢失”。
- **数据证据**：
  - 测试脚本执行结果：
    ```json
    {
      "matchedActorsForLuChen": [
        "陆沉舟",
        "黑衣人头领（对陆沉突施冷箭）",
        "陆沉与苏念",
        "陆沉"
      ],
      "matchedActorsAfterRename": []
    }
    ```
  - 4 项完全不同属性的记录全部被 `陆沉` 命中；改名后命中数归零（0/4）。

### 5. 就地补充与保存

- **判定**：**通过（基础功能通过，但存在交互体验缺陷）**
- **复核项目**：
  1. **就地补充行动与持久化**：
     - 点击 `+ 为「陆沉」补充此事件的可能行动`，填充条件、行动与后果。
     - 切换到角色 1，再切回角色 2；切换其他节点再切回。
     - **结果**：行动内容完整保留，未丢失。
  2. **是否改变首次入场**：
     - 检查 `graph.entries`，补充行动仅修改 `node.possibilities`，未修改角色 `nodeId`、`defaultPath` 或 `knownFacts`。
     - **结果**：完全未改变任何角色首次入场。
  3. **Agent 建议与草稿隔离**：
     - 检查 `CreatorStoryCanvas` 的 `onSave` 传递：
       `onSave={graph => { if (suggested && graphSuggestion) onEditCreatorProposal(graphSuggestion, graph); else if (!suggested) onUpdateStoryGraph(graph); }}`
     - **结果**：在 Agent 建议模式下编辑行动只会更新建议 Change，不会误写入未采纳的草稿。
  4. **上限 6 项边界检查**：
     - 连续添加行动直至 6 项。
     - `disabled={(node.possibilities?.length ?? 0) >= 6}` 触发，按钮变为原生 HTML disabled 状态，无法再添加第 7 项。
     - **交互缺陷**：按钮被禁用时，没有任何辅助提示或 Tooltip 告知创作者“已达到最多 6 项上限”，容易误以为是界面卡死或无响应。
- **截图与数据证据**：
  - 截图证据：`trc_check5_disabled_limit_captured.png`（展示已达到 6 项，按钮置灰禁用）。

## 三、待 Codex 修复问题清单与整改建议

根据 TRC 验收标准，本轮不再重复测试，已停止后续测试，问题统一整理交由 Codex 修复：

### 1. 文案推断修复（解决第 2、3 项）
- **问题**：在 `isAfterEntry` 为 true 时直接宣称“发生此事件时该角色已在局中”，并在汇合节点将互斥分支的登场当成所有走向的既成事实。
- **修改建议**：
  1. **区分多走向汇合与单一走向**：
     - 若该节点的所有上游路径均包含入场点（`paths.every(...)`）：表述为 `「${roleName}」在此走向中已于更早节点登场。`
     - 若仅部分上游路径包含入场点（`paths.some(...)` 但非 `every`）：表述为 `若此前走「${entryNode?.title}」路线，该角色在此事件前已登场；若走其他路线，则尚未入场。`
  2. **中立表述，不推断知情或在场**：
     - 将原文案“发生此事件时该角色已在局中”彻底删除。
     - 改为说明角色与该事件的参与状态取决于现场配置：“未设定是否在场，可补充专属行动或由现场推演”。

### 2. 行动归属机制修复（解决第 4 项）
- **问题**：`actor.includes(roleName)` 导致名字包含混淆、被动目标误判，且角色改名后数据孤立。
- **修改建议**：
  1. **优先使用稳定 RoleId**：在 `Possibility` 结构中支持 `roleId?: string`，绑定到角色草稿 ID（如 `draft-role-1`），改名不丢数据。
  2. **严格等值或定界匹配**：若仍兼容自由文本 `actor`，必须使用精准等值匹配（`p.actor === roleName`），禁止子串宽松 `includes` 双向匹配；对联合行动可使用逗号/顿号显式分词（如 `p.actor.split(/[、,，与]/)` 严格匹配分词项）。
  3. **区分行动主体与交互对象**：避免将带有“（针对某某）”的文本误判为某某的行动。

### 3. 上限交互提示优化（解决第 5 项）
- **修改建议**：当行动项达到 6 项时，在按钮旁展示 `<small className={styles.limitNotice}>已达上限 6 项，如需更多走向建议新建分支节点</small>`，提供清晰预期。
